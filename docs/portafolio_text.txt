1. Alternativa 1: Arquitectura Hexagonal con Eventos
1.1 Descripción de la solución
La plataforma funciona como una sola aplicación organizada por áreas: cuentas, órdenes, portafolios y notificaciones. El usuario realiza su solicitud y puede consultar su avance mientras la plataforma se comunica con el proveedor financiero. Esta organización permite iniciar con pocos recursos y mantener separadas las reglas del negocio de los servicios contratados.
Para Acciones UD, el beneficio es concentrar la operación en un despliegue sencillo sin depender de un único proveedor para todas las funciones. Si cambia el servicio de correo o el proveedor financiero, la integración se puede sustituir sin rehacer la lógica de comisiones y validaciones.
1.2 Aclaraciones técnicas
Aplicación: 
Monolito modular en Java Spring Boot. El dominio contiene comisiones, reservas, validación de tenencias y estados de las órdenes; los puertos y adaptadores conectan Alpaca, Stripe y correo.
Procesamiento de órdenes: 
RabbitMQ
 permite tareas asíncronas. El acuse de recepción de una orden no equivale a su ejecución; la interfaz debe mostrar ambos estados sin confundirlos.
Integridad y recuperación: 
PostgreSQL registra órdenes y movimientos. Se propone patrón 
outbox
, mensajes persistentes, confirmación de entrega, consumidores idempotentes y conciliación con Alpaca para controlar duplicados y fallos.
Consultas de mercado: 
Redis mantiene datos de consulta temporalmente, con fuente y fecha de actualización. Su indisponibilidad no debe modificar saldos ni posiciones.

1.5 Análisis FODA
Factor
Implicación para Acciones UD
Fortalezas
Una sola aplicación simplifica el despliegue y el seguimiento. La separación del dominio facilita probar reglas financieras. Las colas desacoplan notificaciones y tareas de integración.
Oportunidades
Cambiar proveedores mediante adaptadores; incorporar módulos por etapas; extraer una capacidad a un servicio independiente si su crecimiento lo justifica.
Debilidades
El servidor concentra aplicación, datos y mensajería. Una caída del VPS afecta toda la plataforma. Los cambios se publican como una unidad y requieren pruebas de regresión.
Amenazas
Caídas o cambios de condiciones de Alpaca y correo; crecimiento superior al dimensionamiento; acumulación de mensajes si los consumidores no procesan a tiempo.
1.6 Condiciones de operación y alcance
El alcance operativo presupuestado comprende NYSE y NASDAQ, órdenes, fondos de prueba, portafolio, notificaciones y suscripción premium en entorno de prueba. Los módulos de comisionistas y auditoría ampliada, así como LSE, TSE y ASX, requieren aprobación de alcance antes de su implementación.
La meta de 5.000 usuarios registrados, 1.500 concurrentes, respuesta de hasta 2 segundos y confirmación de órdenes de hasta 5 segundos debe verificarse con pruebas de carga e integración. Las configuraciones cotizadas son puntos de partida para un piloto, no una certificación de esa capacidad.
Continuidad: 
La cola reduce el acoplamiento, pero no garantiza por sí sola que una orden nunca se pierda. Deben probarse la persistencia, la recuperación y la conciliación de mensajes con movimientos financieros.
Disponibilidad: 
El servidor único no ofrece alta disponibilidad. Una operación con redundancia requiere otra topología y un presupuesto adicional.
Responsabilidad operativa: 
El equipo administra sistema operativo, actualizaciones, certificados, contenedores, restauración y monitoreo. No se contrata un servicio administrado de base de datos o mensajería.
Dinero y cotizaciones: 
Alpaca 
paper
 trading simula la ejecución y no envía órdenes a una bolsa real. La cuenta Paper 
Only
 ofrece datos IEX y no representa una licencia completa de datos de mercado.
1.7 Consideraciones de implementación
La validación inicial debe demostrar una compra completa: autorización, reserva de fondos, envío a Alpaca, recepción del resultado, actualización del portafolio y notificación. También debe comprobarse el comportamiento ante respuestas tardías, ejecuciones parciales y reintentos.

2. Alternativa 2: Arquitectura 
Microkernel
 con Plug-

2.1 Descripción de la solución
La plataforma se construye alrededor de un núcleo que mantiene las funciones esenciales y recibe extensiones para conectarse con proveedores o incorporar capacidades nuevas. El cliente puede añadir funciones sin sustituir toda la aplicación, siempre que cada extensión respete las reglas de integración del núcleo.
Para Acciones UD, esta opción resulta útil si se prevé ampliar con frecuencia el catálogo de proveedores, tipos de órdenes o servicios adicionales. Su principal inversión está en definir y probar esas reglas de extensión antes de incorporar nuevos módulos.
2.2 Aclaraciones técnicas
Núcleo: 
Java Spring Boot administra identidad, autorización, coordinación de órdenes y transacciones. PostgreSQL mantiene saldos, órdenes y posiciones; los contratos delimitan qué puede modificar cada extensión.
Extensiones: 
Interfaces Java o SPI permiten incorporar conectores de datos, ejecución, pagos y notificaciones. Una interfaz por sí sola no implica instalación en caliente; la carga dinámica debe diseñarse expresamente si se requiere.
Seguridad y premium: 
Los permisos y las suscripciones habilitan o restringen capacidades por usuario. Esta autorización se valida en el servidor y no depende únicamente de activar un 
plug
-in.
Aislamiento: 
Los 
plug-ins
 comparten proceso y recursos con el núcleo. Deben aplicarse tiempos de espera y manejo de excepciones; un fallo grave o consumo excesivo de memoria puede afectar la aplicación completa.

3. Alternativa 3: Microservicios Desplegados en Contenedores
3.1 Descripción de la solución
La plataforma se divide en aplicaciones pequeñas que colaboran entre sí. Cada una atiende un área del negocio, como identidad, órdenes, portafolio o notificaciones. Una función puede actualizarse o recibir más recursos sin publicar de nuevo toda la plataforma, siempre que sus dependencias lo permitan.
Para Acciones UD, esta opción permite organizar equipos o cargas de trabajo por área. A cambio, exige más coordinación: los servicios deben comunicarse de forma segura, mantener sus datos consistentes y permitir localizar una operación a través de varios componentes.
3.2 Aclaraciones técnicas
Servicios: 
Identidad, trading, portafolio, notificaciones/suscripciones y auditoría operativa. El servicio de comisionistas se incorpora solo si se aprueba ese módulo.
Comunicación y datos: 
API de entrada y comunicación HTTP o por eventos. Cada servicio es propietario de sus datos. El piloto puede compartir una instancia física de PostgreSQL con bases y credenciales separadas, sin acceso directo a tablas ajenas.
Consistencia: 
Las operaciones entre servicios requieren idempotencia, 
outbox
, conciliación y acciones compensatorias. No se asume una transacción ACID única entre todos los procesos.
Despliegue: 
Contenedores con configuración y publicación independientes. No se requiere una máquina virtual por servicio ni Kubernetes para que la solución sea de microservicios.
3.3 Infraestructura propuesta
Recurso
Distribución del despliegue
Servidores de aplicación
2 VPS Basic de 4 GiB, 2 
vCPU
 y 80 GiB SSD cada uno. Servicios distribuidos entre ambos; entrada web en uno de ellos.
Servidor de datos
1 VPS Basic de 4 GiB para PostgreSQL, 
RabbitMQ

Frontend
 y dominio
Frontend

Operación

La distribución en tres VPS es una decisión de este despliegue. Compartir hosts reduce aislamiento físico, pero no elimina la independencia de publicación de los servicios.
